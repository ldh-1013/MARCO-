# 문서 작성 규칙 · 모듈 경계 · 권위 모델

> 지금까지의 기획서는 **혼자 읽는 문서**였다. 모호한 부분은 구현하면서 결정하면 됐다.
> 이제는 **4명이 동시에, 서로 묻지 않고 읽는 문서**가 된다. 이건 분량 문제가 아니라 구조 문제다.
>
> 이 문서는 기획서를 고칠 때와 코드를 짤 때 양쪽에 적용된다.

---

# 1. 네 가지 원칙

## 원칙 1 — 모든 수치의 정본은 한 곳

기획서 **부록 A**가 모든 밸런스 상수의 정본이다. 본문 어디에도 숫자를 쓰지 않고
`(§부록 A 참조)`로만 쓴다. 본문과 부록 A가 다르면 **부록 A가 이긴다.**

§16 색상표에 이미 "정본은 하나만 둔다"는 원칙이 있다. 그것을 문서 전체로 확장하는 것이다.

**부록 A의 각 행은 네 칸을 가진다.**

| 항목 | 값 | 근거 | 연동되는 값 |
|---|---|---|---|
| 숨 게이지 | 12초 | 수중 밸브 8초 + 왕복 2초 → 잔여 4초 확보 | 비명 억제 비용(비율 2.67 고정) · 수중 밸브 총 점유 · 배수구 작업 시간 |

**"연동되는 값" 칸이 이 표의 핵심이다.** 혼자 개발할 때는 머릿속에 있던 연결이,
4명이 되면 아무도 모르는 지뢰가 된다. 숨 게이지를 건드린 사람이 §3.5 외침을 약화시켰다는
사실을 모른 채 커밋하는 일을 막는다.

**코드에서도 같다.** 밸런스 수치는 ScriptableObject 하나에 모으고 각 시스템이 거기서 읽는다.
클래스마다 `const float ValveTime = 8f`를 두지 않는다.

## 원칙 2 — 모든 시스템에 권위를 명시

각 시스템에 아래 셋 중 하나를 한 줄로 박는다. **표기가 없는 시스템은 착수하지 않는다.**

| 표기 | 의미 |
|---|---|
| **서버 권위** | 서버가 유일한 결정권자. 클라이언트는 표시만 한다 |
| **클라이언트 예측 허용** | 클라이언트가 먼저 그리되 서버 값이 오면 덮어쓴다 |
| **표시 전용** | 게임 상태에 영향 없음. 순수 연출 |

이게 없으면 A가 짠 시스템은 서버 권위, B가 짠 시스템은 클라 권위가 되어 통합할 때 전부 다시 쓴다.
**판단이 안 서면 추측하지 말고 기획에 묻는다.**

전체 표는 아래 3장에 있다.

## 원칙 3 — 모듈 경계 = 사람 경계

문서의 섹션 구조가 그대로 작업 분담이 된다. 경계를 넘는 호출은 **인터페이스 계약으로만** 한다.
남의 모듈 내부 클래스를 직접 참조하지 않는다. 상세는 아래 2장.

## 원칙 4 — 용어와 코드 식별자를 3열로 고정

§0 용어집을 아래 형식으로 바꾼다. 지금은 파문/SoundPulse, 술래/Seeker가 한영 혼용이라,
4명이 각자 클래스명을 지으면 제각각이 된다.

| 한국어 | 코드 식별자 | 정의 |
|---|---|---|
| 파문 | `SoundPulse` | 소리 발생 시 생성되는 시야 이벤트. 위치·반경·지속·타입을 가짐 |
| 술래 | `Seeker` | 술래 역할. 1인 |
| 도망자 | `Runner` | 밸브를 열고 탈출해야 하는 역할 |
| 메아리 | `Echo` | 태그당해 탈락한 도망자. 유령 상태로 계속 참여 |
| 밸브 | `Valve` | 회전시켜 여는 탈출 게이트 트리거 |
| 역류 | `Reflow` | 개방된 밸브가 시간 경과로 스스로 닫히는 규칙 |
| 차폐 | `Occlusion` | 지형에 의해 파문 인지 반경이 감쇠·차단되는 현상 |
| 인지 배율 | `PerceptionMultiplier` | 역할에 따라 같은 파문을 다르게 감지하는 배율 |
| 노크 | `Knock` | 메아리의 유인 능력 |
| 외침 | `SeekerShout` | 술래 전용 능력. 반경 내 도망자의 자동 비명 유발 |
| 잠행 | `Stalk` | 술래의 저속 이동. 발소리가 걷기급으로 낮아짐 |
| 숨 게이지 | `BreathGauge` | 잠수와 비명 억제가 공유하는 자원 |
| 배수구 | `DrainHatch` | 최후 생존자 전용 탈출구 |
| 최후 생존자 페이즈 | `LastSurvivorPhase` | 도망자가 1명 남았을 때 진입하는 라운드 단계 |
| 잔상 | `Afterglow` | 파문이 지나간 뒤 지형 모서리에 남는 저휘도 윤곽 |
| 캠핑 방지 | `IdleNoise` | 장시간 정지 시 자동 발생하는 호흡음 |

# 2. 모듈 경계와 작업 분담

## 2-1. 계층 구조

Phase 3~4에서 검증된 3계층 구조를 유지한다.

```
Core          — 순수 C#. Unity 의존 없음. 전부 EditMode 테스트 대상
  ↑ 인터페이스로만 연결 ↑
Net           — 네트워크 동기화, 서버 권위 판정
Presentation  — 입력, 카메라, 렌더링, UI
```

**Net과 Presentation은 서로 참조하지 않는다.** 연결이 필요하면 Core에 인터페이스를 두고
양쪽이 그것만 본다. 이 패턴은 차폐 프로브에서 시작해 입력 게이트·플레이어 식별자 등으로
반복 적용됐고, 실제로 잘 작동했다.

## 2-2. 4인 분담 제안

| 담당 | 모듈 | 기획서 절 | 핵심 인터페이스 |
|---|---|---|---|
| **P1 — 파문/차폐** | 차폐 판정, 재판정 트래커, 파문 네트워크 전송, 파문 렌더러 | §5 전체, §16.4 | 차폐 프로브, 파문 전송 브릿지, 파문 수신 싱크 |
| **P2 — 라운드/밸브** | 밸브 상태기계, 역류, 게이트, 승패 판정, 최후 생존자 페이즈, 배수구 | §6 전체, §8 | 밸브 호스트, 라운드 네트워크 브릿지, 게이트 상태 |
| **P3 — 역할/이동** | 역할 배정과 로테이션, 태그, 1인칭 이동, 잠수, 숨 게이지, 외침, 캠핑 방지, 메아리 비행과 노크 | §3, §4 | 로컬 조작 게이트, 플레이어 식별자, 태그 대상, 역할 상태 |
| **P4 — 음성/UI/세션** | 음성 캡처와 분류, 방향 게이지, HUD, 로비, 결과 화면, 설정, 접속 관리 | §12, §13, §5.2, §3.4 | 준비 상태 레지스트리, 접속 서비스 |

**맵 제작(§10)은 디자이너가 맡되, 차폐 태그와 바닥 재질 태그 배선은 P1이 검수한다.**
태그가 빠지면 차폐와 재질 배율이 조용히 무효화되기 때문이다(구현 검증 노트 VN-16, VN-17).

## 2-3. 교차 지점 — 여기만 계약으로 고정한다

문서의 절 구조는 대체로 담당과 잘 맞지만, 아래 네 곳은 두 사람 이상이 걸친다.
**이 지점들은 착수 전에 인터페이스를 먼저 합의하고, 이후 시그니처를 바꾸려면 양쪽 동의가 필요하다.**

| # | 교차 | 걸리는 사람 | 계약 내용 |
|---|---|---|---|
| **X1** | 파문 ↔ 맵 지오메트리 | P1 · 디자이너 | 차폐 태그 규약(벽 1장 = 콜라이더 1개), 바닥 재질 태그, 수면 볼륨 |
| **X2** | 밸브 ↔ 파문 | P2 · P1 | 밸브 회전음(12m), 역류 물소리, **수중 강제 파문(2.5초 주기)** 의 발행 경로 |
| **X3** | 잠수 ↔ 차폐 ↔ 밸브 | P3 · P1 · P2 | 수면 존 판정, 수면 차폐 ×0.5, 수중 밸브 진입/부상 타이밍, 배수구 |
| **X4** | 음성 ↔ 차폐 ↔ 방향 게이지 | P4 · P1 | 등급 분류 결과의 파문 변환, "§5.6 통과 펄스만 게이지 트리거" 규칙 |

**X3이 가장 위험하다.** 세 명이 동시에 물리고, 그 위에 §6.5 배수구 설계 전체가 얹혀 있으며,
잠수는 한 번도 구현된 적이 없다(구현 검증 노트 UV-1). **여기는 인터페이스 합의를 가장 먼저 한다.**

## 2-4. 기획 결정과 무관한 선행 작업

기획서 패치가 끝나기를 기다리며 놀지 않기 위한 목록. 첫날 넘길 수 있다.

| 담당 | 착수 가능 |
|---|---|
| P1 | 차폐 판정 순수 함수 + EditMode 테스트, 진단 로그 포맷, 재판정 트래커 |
| P2 | 상태기계 골격(값은 상수 테이블에서 읽도록), 서버 권위 패턴 확립 |
| P3 | 입력 시스템, 1인칭 카메라, 캐릭터 컨트롤러, 키 바인딩 테이블 |
| P4 | 음성 캡처, 밴드패스 80~3400Hz, 등급 분류 (수치가 이미 검증됨) |
| 공통 | 프로젝트 셋업, 어셈블리 정의, 빌드 파이프라인, 테스트 하네스, 씬 부트스트랩 |

# 3. 권위 모델 통합표

기획서 곳곳에 흩어진 권위 서술을 한 표로 모은 것이다. **이 표가 정본이다.**

| 시스템 | 권위 | 비고 |
|---|---|---|
| 차폐 판정 | **서버 권위** | 청취자별 개별 계산. 프로브 미등록 시 판정 중단(fail-closed) |
| 파문 전송 | **서버 권위** | 클라이언트는 **소리 종류만** 주장. 반경·지속은 서버가 표에서 재계산, 위치·ID는 호출자에서 읽음 |
| 파문 렌더링 | 표시 전용 | 서버가 계산한 값을 그대로 그린다. 클라이언트가 추가 배율 연산을 하지 않는다 |
| 본인 파문 즉각 피드백 | 표시 전용 | 로컬 마이크 진폭 직결. 파문 시스템과 별개 |
| 밸브 진행도 | **서버 권위** | 클라이언트는 예측 표시만 |
| 밸브 상호작용 거리 | 클라이언트 판정 | ⚠ 위치 스푸핑 방지는 범위 밖(안티치트 과투자 금지 방침) |
| 역류 타이머 | **서버 권위** | 밸브별 독립 |
| 게이트 개방 | **서버 권위** | latch. 한 번 열리면 유지 |
| 태그 판정 | **서버 권위** | 서버가 거리·대상 역할·이미태그됨을 재검증. 술래 역할·ID는 호출자에서 읽음 |
| 역할 배정 | **서버 권위** | 클라이언트가 역할을 주장할 수 없다 |
| 역할 전환 (러너→메아리) | **서버 권위** | |
| 라운드 타이머 | **서버 권위** | 각 클라이언트가 로컬 타이머를 돌리지 않는다 |
| 승패 판정 | **서버 권위** | 라운드 종료 시 1회 평가 |
| 최후 생존자 페이즈 진입 | **서버 권위** | 생존 도망자 수는 서버만 안다 |
| 배수구 활성 선택 | **서버 권위** | 무작위 1개. 선택 결과를 양 진영에 전송 |
| 배수구 진행도 | **서버 권위** | 밸브와 동일 |
| 탈출 확정 | **서버 권위** | 게이트 상태·역할을 호출자에서 읽고 재검증 |
| 활성 밸브 선택 | **서버 권위** | 라운드 시작 시 1회. 브리핑에서 양 진영 공개 |
| 숨 게이지 | **서버 권위** | 클라이언트 HUD 표시에는 동기화 변수 필요 |
| 외침 발동 | **서버 권위** | 선딜레이 취소 판정 포함 |
| 자동 비명(외침 효과) | **서버 권위** | 공포 반경은 차폐 미적용 직선거리 |
| 캠핑 방지 자동 소리 | **서버 권위** | 20초 슬라이딩 윈도우 누적 이동거리 |
| 노크 발생 | **서버 권위** | 횟수·쿨다운 서버 관리. 발생 위치는 요청 시점 위치로 고정 |
| 플레이어 이동 | 클라이언트 권위 | ⚠ 현행 방침. 위치 스푸핑 방지는 범위 밖 |
| 낙하 리스폰 | 클라이언트(소유자) | 라운드 결과를 바꾸지 않으므로 서버 왕복 불필요 |
| 음성 등급 분류 | 클라이언트 | 마이크는 로컬에만 있다. 분류 **결과**만 서버로 |
| 방향 게이지 | **서버 권위** | §5.6 통과 펄스만 트리거. 표시는 클라이언트 |
| 준비 상태 / 로비 | **서버 권위** | 카운트다운 중 토글 무시 |
| 설정 | 로컬 | 게임 상태에 영향 없음 |

**⚠ 표시가 붙은 세 항목(밸브 거리 판정, 플레이어 이동, 그에 따른 위치 스푸핑)은 의도적으로
남겨둔 구멍이다.** 친구 간 플레이를 전제로 안티치트에 과투자하지 않는다는 방침이며,
**새 구현에서도 같은 판단을 유지하되 "모르고 뚫린 것"과 구분되도록 여기에 명시한다.**

# 5. 예외 케이스 — 가장 많이 빠지는 부분

각각 "어떻게 되는가"를 기획서에 한 줄씩 명시한다. 여기 비어 있는 칸이 곧 미해결 설계 결함이다.

## 5-1. 중단과 이탈

| 상황 | 처리 |
|---|---|
| 밸브 작업 중 탈락 | 진행도 감쇠 시작(리셋 아님). 다른 도망자가 즉시 이어받을 수 있다 |
| 밸브 작업 중 연결 끊김 | 위와 동일. 밸브를 잠그지 않는다 |
| 수중에서 탈락 | **미정의** — 시신 처리, 강제 부상 여부 |
| 배수구 작업 중 탈락 | 해당 없음(최후 생존자이므로 탈락 = 라운드 종료) |
| 라운드 중 도망자 이탈 | 탈출 요구 인원을 재계산하는가, 라운드 시작 시점 값을 고정하는가 — **결정 필요** |
| **라운드 중 술래 이탈** | **미정의** — 가장 자주 빠지는 케이스 |
| 최후 생존자 이탈 | 페이즈 즉시 종료, 술래 승리 |

## 5-2. 동시 발생

| 상황 | 처리 |
|---|---|
| 탈출과 태그가 같은 프레임 | 탈출 우선 |
| 시간 종료와 탈출이 같은 프레임 | 탈출 우선 |
| 페이즈 진입과 탈출이 같은 프레임 | 탈출 먼저 확정. 도망자 0명이면 페이즈 미진입 |
| 두 도망자가 같은 밸브를 동시에 | 동시 작업 배율 적용(2인 ×1.6) |
| 부상 완료와 게이지 고갈이 같은 시점 | 부상 완료 우선 — 성공으로 확정 |
| 역류 완료와 3번째 밸브 완료가 같은 프레임 | 동시 개방 수를 그 시점에 평가 |

## 5-3. 페이즈 경계

| 상황 | 처리 |
|---|---|
| 게이트가 이미 열린 상태에서 페이즈 진입 | 배수구를 활성화하지 않는다. 기존 출구를 쓴다 |
| 페이즈 중 라운드 제한시간 종료 | 더 짧은 쪽이 우선 |
| 메아리가 노크한 직후 라운드 종료 | 노크 파문은 라운드 종료와 함께 소멸 |
| 종반 압박(잔여 1분) 중 페이즈 진입 | 두 효과가 동시에 적용된다 |

# 6. 문서를 고칠 때

1. 값을 바꾸면 **부록 A를 먼저** 고치고, 그 행의 "연동되는 값" 칸을 확인한다
2. 연동된 값이 있으면 **함께 고치거나, 왜 안 고치는지 근거를 남긴다**
3. 결정 로그에 날짜·변경 내용·근거를 남긴다
4. 절을 삭제하면 그 절을 참조하는 다른 절을 전부 찾아 정리한다
   (§11 폐극장 삭제 시 §5.6 `HardBlocker`·§5.9 나무 마루·§18 맵 목록이 함께 걸렸다)

**"왜 이 값이죠?"라는 질문에 매번 구두로 답하지 않기 위한 것이다.**
