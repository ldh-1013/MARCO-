# 밸브 시스템 구현 지시서 — 7-A / 7-B

> 기획서 v0.3(§6.1-0 / §6.1-2 / §6.2-1 / §6.3 / §10.2) 반영 작업.
> **각 절의 코드블록을 그대로 Claude Code에 붙여넣는다.** 한 단계가 끝나면 기획이 검수하고, 통과한 뒤 다음 단계로 간다.

| 항목 | 값 |
|---|---|
| 총 단계 | **8단계** (7-A 4단계 · 7-B 4단계) |
| 시작 시점 테스트 | 732케이스 |
| 선행 미결 | **탈출자 관전 규칙**(미정) — 7-B-1 착수 전까지 결정 필요 |

---

## 0. 왜 8단계로 쪼개는가

밸브 변경은 판정(Core) → 전파(Net) → 표시(Presentation)가 한 줄로 이어져 있다. 한 번에 묶으면 **역류 버그와 승리조건 버그가 섞여 원인 분리가 불가능해진다.** 실제로 이 프로젝트에서 `ServerKnockDriver.Reset()` 호출부 부재 같은 결함은 **범위를 좁혔기 때문에** 잡혔다.

각 단계는 **단독으로 테스트가 통과하고, 단독으로 검수 가능한 크기**다.

## 1. 공통 규칙 — 모든 단계에 적용

### 1.1 더블체크 10항목 (매 단계 필수)

> **이 10항목은 이 프로젝트에서 실제로 사고가 났던 지점들이다.** 구현을 끝낸 뒤 반드시 하나씩 확인하고, 보고서에 **결과표를 포함**한다. "확인했다"가 아니라 **무엇을 어떻게 확인했는지** 쓴다.

| # | 항목 | 확인 방법 | 과거 사고 |
|---|---|---|---|
| **1** | **호출부 존재** | 새로 만든 public 메서드·상태를 **프로덕션 코드가 실제로 호출하는가.** 테스트만 부르고 있지 않은가 | `ServerKnockDriver.Reset()` 호출부가 아예 없어 2라운드부터 노크 영구 봉인 |
| **2** | **라운드 전이 초기화** | 라운드가 바뀔 때 새 상태가 리셋되는가. 2라운드에서 살아남는 값이 없는가 | 같은 사건 |
| **3** | **경계값** | 정확히 임계값일 때(150.0초, 3개째 개방 순간, 0초)의 동작을 테스트로 고정했는가 | 밸브 B 게이지 0초 경계(§6.1-1) |
| **4** | **기존 테스트 의미 변화** | 이름은 그대로인데 뜻이 바뀐 테스트가 없는가. 있으면 **이름부터 고친다** | 3단계에서 `TwoTagged_SeekerWinsImmediately` 의미 변화 |
| **5** | **서버 권위(GAP-24)** | 클라이언트 주장값을 믿는 곳이 없는가. 위치·시간·상태를 서버가 재계산하는가 | 노크 좌표를 클라가 보내던 구조 |
| **6** | **캐시 금지(GAP-61)** | `LocalPlayerRegistry.Current`를 필드에 굳히지 않았는가. 매 프레임 재조회하는가 | 원격 pawn을 붙잡아 4곳에서 오작동 |
| **7** | **계층 경계** | Core에 `UnityEngine.Time`·`Input`·`Physics`·FishNet이 들어가지 않았는가 | EditMode 테스트가 성립하는 유일한 근거 |
| **8** | **상수 중복** | 같은 값이 두 곳에 없는가. 유도 가능하면 계산으로 유도했는가 | `MaxConsecutiveSuppressions => (int)(8/3)` 방식이 정답 |
| **9** | **enum 파급** | enum에 값을 추가했다면 그것을 읽는 `switch`·`if` 전수를 확인했는가 | `RoundResult` 변경이 HUD까지 파급 |
| **10** | **문서 정합** | 기획서 수치와 코드 상수가 **전부** 일치하는가. 주석의 기획서 인용문도 최신인가 | `KnockConfig` 주석이 구버전 §3.2를 인용 중이었음 |

### 1.2 보고 형식 (매 단계 필수)

```
① 변경 전/후      — 값·조건식·시그니처를 나란히
② 계산 검증표     — 경계값 포함. "~할 것이다"가 아니라 실제 수치
③ 더블체크 10항목 — 10개 전부. 각 항목에 "무엇을 어떻게 확인했는지"
④ 테스트          — 신규·갱신 케이스명과 통과 여부
⑤ 전체 재검증     — 전 어셈블리 오류/경고, 테스트 총계 변화
⑥ 범위 밖으로 남긴 것 — 발견했지만 이번에 안 고친 것
```

**문제가 하나라도 남으면 PASS라고 보고하지 않는다.**

### 1.3 중단 규칙

**지시와 기존 기록(기획서·빌드로그·GAP 목록)이 충돌하면 실행하지 말고 먼저 알린다.** 이 규칙으로 지시 오류 1건을 이미 잡았다(C1 조건식 방향).

### 7-A-2 — 역류(Reflow) 타이머

```
기획서 §6.1-2 밸브 역류를 구현해라. 이번 단계가 7-A에서 가장 위험하다.

[규칙 — §6.1-2 원문]
- 개방 유지 150초 → 역류 30초에 걸쳐 폐쇄 → Closed(진행도 0)
- 역류 중 재상호작용해서 회전을 완료하면 Open 복귀 + 타이머 리셋
- 타이머는 밸브별 독립. 각자 Open이 된 순간부터 센다
- 회전 시간은 최초와 동일

[작업]
1. Core/Objectives/Valve.cs
   ReflowGraceSeconds = 150f, ReflowDurationSeconds = 30f 상수 추가.
   Open 상태 진입 시각을 기록하고, Tick에서 경과를 보고 Reflowing → Closed로 전이.
   Reflowing 중 TryBeginRotation이 가능해야 한다(Closed와 동일하게 취급).

2. 역류 진행도
   Reflowing 구간의 잔여 시간을 외부에서 읽을 수 있게 공개한다(HUD·네트워크용).
   0~1 정규화 값이 아니라 초 단위로 준다 — HUD가 초를 표시해야 한다.

[반드시 확인할 것 — 과거 사고 재발 방지]
★ Valve.Tick()을 실제로 호출하는 프로덕션 코드가 있는지 먼저 확인해라.
  ServerValveDriver가 부르고 있는지, 매 프레임 부르는지, 라운드 중에만 부르는지.
  호출부가 없거나 조건부라면 역류가 영영 작동하지 않는다. (더블체크 1)
★ 라운드가 끝나고 새 라운드가 시작될 때 Open 진입 시각이 리셋되는지 확인해라.
  리셋되지 않으면 2라운드에서 밸브가 즉시 역류한다. (더블체크 2)

[계산으로 증명할 것]
- t=149.9초: Open 유지
- t=150.0초: Reflowing 진입 (경계)
- t=179.9초: Reflowing 유지
- t=180.0초: Closed (경계)
- t=150~180 사이에 회전 완료 → Open 복귀 + 타이머가 0부터 다시 시작하는지

[테스트]
위 경계값 5종 + 밸브별 독립성(A가 역류해도 B 타이머는 영향 없음)
+ 역류 중 회전 완료 시 리셋 + 라운드 리셋 시 타이머 초기화

[보고] 공통 규칙 1.2 형식. 더블체크 10항목 전부.
지시와 기존 기록이 충돌하면 실행하지 말고 먼저 알려라.
```

### 7-A-3 — 5개 중 4개 무작위 활성

```

[규칙]
- 맵에 5개(A~E) 배치, 매 라운드 서버가 4개를 무작위 선택
- 비활성 밸브는 상호작용 불가

- 활성 4개 중 3개만 열어도 요구 충족(개수 판정은 7-A-4에서, 여기선 활성 여부만)

[보고] 공통 규칙 1.2 형식. 더블체크 10항목 전부.

### 7-A-4 — 게이트 동시 개방 판정 + Latch

```
기획서 §6.1-2 "출구 게이트는 한 번 열리면 유지된다" 를 구현해라.

[규칙]
- 활성 밸브 중 3개가 "동시에" Open이면 게이트 Open
- 게이트는 latch — 한 번 열리면 역류로 밸브가 닫혀도 다시 닫히지 않는다
- 요구 개수는 §6.2 인원별 표를 따른다(4인 기준 3)

[작업]
1. 게이트 판정 위치를 먼저 조사해라.
   현재 EscapeGateRegistry / IEscapeGateState.IsGateOpen이 있다.
   누가 IsGateOpen을 세팅하는지, 지금은 무엇을 기준으로 하는지 파악한 뒤
   가장 자연스러운 지점에 동시 개방 수 판정을 넣어라. 새 클래스를 만들지 마라.

2. 판정식
   simultaneouslyOpenValves >= requiredValves  →  gateOpened = true (이후 유지)
   "누적 개방 수"가 아니라 "지금 Open인 밸브 수"다. 역류로 줄어들 수 있다.

[반드시 확인할 것 — 이 단계의 핵심 함정]
★ 기존 코드가 "한 번 Open이면 영원히 Open"을 전제로 밸브 개수를 세고 있지 않은지
  전수 확인해라. 역류가 생기면서 그 전제가 깨졌다. 카운터를 증가만 시키는 코드가
  있다면 전부 찾아내야 한다. (더블체크 9 — enum은 아니지만 같은 성격의 파급)
★ 게이트가 열린 뒤 밸브가 역류해도 TryRegisterEscape가 계속 성공하는지 확인해라.
  ServerRoundDriver.TryRegisterEscape(playerId, role, gateOpen)에 gateOpen이
  어디서 오는지 추적해라.
★ 라운드 리셋 시 gateOpened가 false로 돌아가는지(더블체크 2).

[계산으로 증명할 것]
- 활성 4개 중 2개 Open → 게이트 닫힘
- 3개째 Open되는 순간 → 게이트 열림 (경계)
- 그 후 1개가 역류로 Closed → 동시 개방 2개지만 게이트는 여전히 Open
- 게이트 Open 상태에서 탈출 등록이 성공하는지

[테스트]
위 4종 + 라운드 리셋 + 요구 개수를 3이 아닌 값으로 줬을 때도 동작하는지

[보고] 공통 규칙 1.2 형식. 더블체크 10항목 전부.
지시와 기존 기록이 충돌하면 실행하지 말고 먼저 알려라.
```

### 7-B-1 — 승리조건 전환

```
기획서 §6.3 승패 판정을 gateOpened 기준으로 바꿔라.
※ 이 코드는 3단계에서 이미 한 번 고쳤다. 당시 테스트의 의미가 바뀌므로 주의해라.

[변경]
이전: Evaluate(valvesOpened, totalValves, runnersEscaped, taggedRunners, timeRemaining)
       if (totalValves > 0 && valvesOpened >= totalValves && runnersEscaped >= 2)
이후: Evaluate(gateOpened, runnersEscaped, taggedRunners, timeRemaining)
       if (gateOpened && runnersEscaped >= EscapeWinThreshold)

- EscapeWinThreshold(2) / TagWinThreshold(2)는 그대로 유지
- 판정 순서(탈출 → 태그 → 시간 종료)도 그대로
- totalValves 매개변수는 제거한다. 게이트 판정으로 옮겨갔다(7-A-4)
