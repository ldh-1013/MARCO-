## 0. 이 문서의 목적

1인 개발 프로토타입(Phase 4까지)은 끝났고, 팀 6명이 기획서를 기준으로 **새 레포에서 새로 개발한다.** 프로토타입 코드는 참고용 기록이다 — 가져다 쓰는 경우 이슈 + PR로 이식하고 기획서 기준으로 다시 검증한다(`작성규칙/작성규칙_상세판.md` 4.4). 프로토타입에서 확인한 구조(3계층 분리, 서버 권위 원칙, GAP 추적, 정본 문서 체계)를 **누가 어디까지 책임지는가**로 옮기는 것이 이 문서의 전부다.

핵심 전제 하나: **이 프로젝트는 코드보다 문서가 먼저다.** 수치와 규칙은 전부 기획서에서 오고, 코드는 그것을 옮긴 결과물이다. 구현하다 막혔다고 수치를 창작하면 나중에 반드시 어긋난다(이 프로젝트에서 이미 2회 발생).

## 2. 팀 구성과 역할 배분

### 2.1 전체 배분표

| 역할 | 인원 | 한 줄 정의 |
|---|---|---|
| 기획 | 1 | 정본 소유자 · 수치 결정권자 · 최종 검수(PR 병합 승인자는 아님 — `작성규칙/작성규칙.md` 규칙 2) |
| P1 — Core 게임 로직 | 1 | 밸브 · 승리조건 · 태그 · 역할 · 어워드 |
| P2 — 사운드/파문 시스템 | 1 | SoundPulse · 음성 · 노크 · 외침 · 숨 게이지 |
| P3 — 네트워크/인프라 | 1 | FishNet 동기화 · 서버 권위 · 빌드 · 성능 |
| P4 — Presentation/UX | 1 | 컨트롤러 · 카메라 · 입력 · HUD · 결과화면 |
| 디자인 | 1 | 아트 디렉션 전반 · 맵 미감 · UI 비주얼 · 스토어 자산 |

분업 축을 **계층(Core/Net/Presentation)** 이 아니라 **계층 + 시스템 혼합**으로 잡은 이유: 사운드/파문 계열이 이 게임의 유일한 핵심 훅이면서 Core·Net·Presentation 세 계층에 모두 걸쳐 있어, 계층으로만 나누면 가장 중요한 시스템에 오너가 없어진다.

---

### 2.2 기획 (1명)

| 구분 | 내용 |
|---|---|
| 소유 문서 | `마르코_상세기획서.md`(**유일 정본**), `맵설계.md`, `연출.md`, `작성규칙/작성규칙.md`, `README.md`(문서 안내) |
| 결정 권한 | 모든 수치, 규칙, 승리조건, 밸런스, 시스템 추가/삭제 여부 |
| 상시 업무 | GAP 트리아지·우선순위 배정, 구현 결과 검수, 실기 플레이테스트 진행, 스프린트 계획 |
| 하지 않는 일 | 직접 구현(예외: 문서 수정) |

**검수가 이 역할의 본체다.** 구현자가 낸 결과를 "좋다"고 승인하는 게 아니라, 수치를 다시 계산하고 코드를 직접 열어 보고서와 대조한다. 실제로 이 방식으로 지금까지 지시 오류 1건(내가 반대로 쓴 조건식)과 치명 결함 1건(`ServerKnockDriver.Reset()` 호출부 부재 — 2라운드부터 노크 영구 봉인)을 잡았다. 단 새 개발에서 PR 병합 승인자는 기획이 아니다 — 승인은 작성자가 아닌 프로그래머 1명이고, 기획은 `docs/` PR을 올리는 주체다(`작성규칙/작성규칙.md` 규칙 2).

## 4. 협업 매트릭스 — 누구와 무엇을 함께 하는가

### 4.1 상시 접점

| 접점 | 무엇을 공유하는가 | 누가 소유하는가 | 조율 규칙 |
|---|---|---|---|
| **P1 ↔ P3** | 밸브 상태·승리 판정의 네트워크 전파 | 판정 = P1(Core) / 전파 = P3(Net) | P1이 규칙을 확정한 뒤 P3가 전파를 붙인다. **순서를 뒤집지 않는다** |
| **P1 ↔ P4** | `RoundResult`·`ValveState` enum | enum = P1 | **enum 변경은 같은 커밋에서 양쪽 동시 처리.** P4에 알리지 않은 enum 변경은 결과화면을 조용히 깨뜨린다 |
| **P2 ↔ P3** | 파문의 서버 권위 전파 | 판정 = P2(Core) / 전파 = P3(Net) | `IPulseNetworkBridge` 변경은 **양쪽 합의 후에만** |
| **P2 ↔ P4** | 파문 시각화·방향 게이지 | 판정 = P2 / 표현 = P4 | 판정과 표현을 절대 섞지 않는다. P4는 P2가 준 결과를 그리기만 한다 |
| **P2 ↔ 디자인** | 바닥 재질 태그 | 태그 정의 = P2 / 씬 적용 = 디자인 | 디자이너가 구역을 만들 때 **재질 태그를 함께 붙인다.** 나중에 일괄로 붙이면 반드시 빠진다 |
| **P4 ↔ 디자인** | 아트 자산의 씬·프리팹 반영 | 에셋 = 디자인 / 배선 = P4 | 디자이너는 `.fbx`·머티리얼까지, 씬에 꽂는 것은 P4 |
| **디자인 ↔ 기획** | 맵 레이아웃 | 구역 규격·밸브 배치 = 기획 / 블록아웃 = 디자인 | 좌표는 `docs/맵설계.md`, 디자인이 만든 뒤 **기획이 맵 지표(§10.2 · §10.2-1)를 검증** |
| **전원 ↔ 기획** | 모든 수치 | 기획서 = 기획 | 코드에 수치를 창작하지 않는다. 기획서에 없으면 **GAP으로 기록하고 물어본다** |

### 4.2 공동 제작이 필요한 작업 (혼자 못 끝내는 것)

| 작업 | 참여자 | 왜 함께 해야 하는가 | 진행 방식 |
|---|---|---|---|
| **7-B 승리조건·이벤트·태그** | P1 + P3 + P4 | 판정(P1) → 전파(P3) → 표시(P4)가 한 줄로 이어져 있어 따로 만들면 접합부에서 깨진다 | P1이 먼저 규칙 확정 → P3·P4 동시 착수 → 셋이 함께 통합 테스트 |
| **물 볼륨 감지** | P2 + P4 | 물 판정(Core 규칙)과 콜라이더 감지(Presentation)가 한 몸 | P2가 `ZoneOf` 입력 계약을 정하고, P4가 그 값을 채운다 |
| **새 맵 블록아웃** | 디자인 + 기획 (+P2) | 치수·밸브 배치는 밸런스 사안, 블록아웃은 아트, 재질 태그는 사운드 | 맵설계.md 좌표 → 디자인 블록아웃 → 기획 맵 지표 검증 → P2 재질 태그 |
| **실기 검증** | **전원(최소 3인)** | 혼자서는 태그 2명 도달조차 재현할 수 없다 | 주 1회 고정 시간, 호스트 1 + exe 2 |
| **재질 태그 배선** | P2 + 디자인 | 태그 정의는 코드, 부착은 씬 | 디자이너가 구역 제작 시 동시에 부착 |

### 4.3 절대 혼자 결정하면 안 되는 것

| 항목 | 반드시 합의할 상대 | 이유 |
|---|---|---|
| `enum` 값 추가·변경 | 그 enum을 읽는 전원 | 컴파일은 되는데 런타임에 조용히 틀려진다 |
| 인터페이스 시그니처 변경 | 구현체·호출부 소유자 | 계층 경계가 무너진다 |
| 기획서 수치 | **기획** | 코드가 정본이 되는 순간 문서 체계가 붕괴 |
| 씬·프리팹 구조 변경 | 6절 편집권 규칙에 따라 전원 공지 | 머지 불가능 |

## 5. 회의 구조

> **회의는 네 종류면 충분하다.** 이보다 늘리지 않는다 — 6명짜리 팀에서 회의가 늘면 그게 곧 개발 시간 손실이다.

| 회의 | 주기 | 참석 | 시간 | 목적 |
|---|---|---|---|---|
| **스프린트 킥오프** | 주 1회 | 전원 | 30분 | 이번 주 작업 배분, 선행 조건 확인, 블로커 공유 |
| **실기 플레이테스트** | 주 1회 | **최소 3인** | 60분 | 실기 검증 체크리스트 실행 + 버그 발견 |
| **인터페이스 합의** | 필요시 | 관련자만 | 15분 | enum·인터페이스 변경 전 5분 대화. **이걸 건너뛰면 하루를 잃는다** |
| **아트 리뷰** | 격주 | 디자인 + P4 + 기획 | 30분 | 컨셉·모델·UI 방향 확인, 팔레트 준수 점검 |

### 5.1 스프린트 킥오프에서 반드시 확인할 것

| 항목 | 확인 내용 |
|---|---|
| 선행 조건 | 이번 주 작업 중 다른 사람 완료를 기다리는 것이 있는가 |
| 씬·프리팹 | 이번 주에 씬/프리팹을 건드릴 사람이 있는가 (**충돌 예방**) |

| 단계 | 내용 |

## 6. 공동 작업 규칙

### 6.1 씬·프리팹 편집권 (가장 먼저 사고가 나는 지점)

> Unity 씬(`Lobby.unity` · `Game.unity`)과 `Player.prefab`은 **텍스트 머지가 사실상 불가능하다.** 두 사람이 동시에 건드리면 한쪽 작업이 통째로 사라진다.

| 규칙 | 내용 |
|---|---|
| **선점 공지** | 씬·프리팹·공용 에셋을 여는 순간 고정 이슈 "공용 파일 선점 현황"에 "`Game.unity` 잡습니다" 댓글 — 세부는 `작성규칙/작성규칙_상세판.md` 3.4 |
| **해제 공지** | 커밋·푸시 후 같은 이슈에 "놨습니다" 댓글 |
| **동시 편집 금지** | 공지된 파일은 다른 사람이 열지 않는다 |
| **장시간 점유 금지** | 반나절 이상 잡아야 하면 킥오프에서 미리 알린다 |
| **충돌 시** | 머지하지 말 것. **나중에 잡은 쪽이 자기 작업을 다시 한다** |

### 6.2 커밋 규칙

| 규칙 | 내용 |
|---|---|
| enum·인터페이스 변경 | **영향받는 전체를 같은 커밋에** 넣는다 |
| 테스트 | 코드와 **같은 커밋**에. 나중에 붙이면 안 붙는다 |
| 문서 | **기획서는 기획만 고친다.** 구현이 기획서와 달라져야 하면 `[GAP]` 이슈로 요청하고, 기획서 PR이 먼저 병합된 뒤 코드를 올린다 — `작성규칙/작성규칙.md` 규칙 1(세부 `작성규칙/작성규칙_상세판.md` 1.3 · 1.5절) |
| 빌드 깨진 상태 | 푸시 금지. 732케이스 통과가 기본선(프로토타입 기준) |

### 6.3 GAP 등록은 누구나, 판단은 기획

| 단계 | 담당 |
|---|---|
| 기획서에 정의가 없다는 것을 발견 | **누구나** |
| GAP 이슈 등록(`[GAP] §절 질문`, `gap` 라벨) — 새 GAP은 이슈 번호 `#N`, 프로토타입 GAP은 "프로토 GAP-N" | 발견자 |
| 해석·결정 | **기획만** — 24시간 안에 1차 답변(`작성규칙/작성규칙_상세판.md` 1.5) |
| 임시로 코드에 값을 넣는 것 | **금지.** 막히면 물어본다 |

## 7. 작업 프로세스

> 7.1 · 7.2는 프로토타입 시기의 절차다. 새 개발의 PR · 리뷰 · 완료 기준은 `작성규칙/작성규칙.md` 규칙 2(승인 = 작성자가 아닌 프로그래머 1명)가 정본이고(세부 `작성규칙/작성규칙_상세판.md` 2 · 5절), 작업 단위는 GitHub 이슈(`작성규칙/작성규칙_상세판.md` 6.1)다.

### 7.1 스프린트 운영

현재 스프린트 번호(27+)를 그대로 이어간다. 1스프린트 = 1~5일 규모의 명확한 단위 작업.

```
① 기획이 정본에 규칙·수치 확정 반영
② 담당 오너가 구현 (+ EditMode 테스트 동시 작성)
③ 기획이 검수 — 코드 직접 대조, 수치 재계산
④ 통과 시 커밋 · 이슈 · PR에 기록
⑤ 실기 검증 (누적해서 일괄 진행)
```

### 7.2 구현 → 검수 절차

구현자는 완료 보고 시 **반드시** 아래를 포함한다. 형식이 지켜지지 않으면 검수가 불가능하다.

| 항목 | 내용 |
|---|---|
| 변경 전/후 | 값·조건식·시그니처를 나란히 |
| 계산 검증표 | "~할 것이다"가 아니라 실제 수치 계산. 경계값 포함 |
| 테스트 | 신규·갱신 케이스명과 통과 여부 |
| 전체 재검증 | 전 어셈블리 오류/경고, 테스트 총계 변화 |
| 범위 밖으로 남긴 것 | 발견했지만 이번에 안 고친 것 |

**문제가 하나라도 남으면 PASS라고 보고하지 않는다.**

**지시와 기존 기록(빌드로그·GAP 목록·기획서)이 충돌하면 실행하지 말고 먼저 알린다.** 실제로 이 규칙 덕에 기획의 지시 오류를 구현자가 잡아낸 사례가 있다.

### 7.3 GAP 관리

기획서에 정의가 없거나 모순이 있는 지점은 **창작하지 않고 GAP으로 기록**한다. (프로토타입에서 GAP-1~104까지 추적했다.)

| 상태 | 의미 |
|---|---|
| ✅ 해소 | 기획서 보완 또는 구현으로 종결 |
| ⏭ 이월 | 선행 시스템 부재로 뒤 단계에서 처리 |
| 📌 결정 유지 | 의도적으로 현 상태를 유지하기로 결정 |

기록 위치: **GitHub 이슈(`gap` 라벨)**. 결정 내용은 기획서 §0 개정 이력 + `개정이력_YYYY-MM-DD.md`에 남긴다 — 세부는 `작성규칙/작성규칙_상세판.md` 1.5절. 프로토타입 GAP-1~104의 기록은 레포 문서에 남아 있지 않다(`archive/프로토타입_지시서/` 참고).

### 7.4 실기 검증

| 단계 | 내용 |
|---|---|
| 0 | exe 재빌드(스크립트·프리팹 변경 시 필수). **최소 3인**(호스트 1 + exe 2) — 2인은 태그 2명 도달이 불가능해 절반 이상 검증 불가 |
| 1 | 스모크: 이동·발소리·태그·밸브·탈출 |
| 2 | 신규 기능(실기 검증 체크리스트 — 새 레포에서 작성) |
| 3 | 버그 트리아지 → 이슈 등록(`버그` · `gap` 라벨) → 우선순위 분류 |
| 4 | 수정 후 재검증 |
| 5 | 인원별 확장 테스트(3~6인 모두 정식 밸런스 — 기획서 §1) |

## 9. 코드 규칙 (계층 경계)

| 계층 | 허용 | 금지 |
|---|---|---|
| **Core** | 순수 C# 로직, 규칙, 상태기계 | `UnityEngine.Time`·`Input`·`Physics` 참조, `MonoBehaviour`, FishNet 참조 |
| **Net** | FishNet, 서버 권위 판정, 동기화 | 게임 규칙을 여기서 새로 정의하는 것 |
| **Presentation** | MonoBehaviour, 렌더링, 입력, UI | 판정 로직을 여기서 수행하는 것 |

**Core가 순수해야 EditMode 테스트가 성립한다.** 이 프로젝트가 732케이스(프로토타입 기준)를 유지할 수 있는 유일한 이유다.

추가 규칙:
- 새 상수를 만들기 전에 기존 상수 재사용 가능성을 먼저 확인한다(값이 두 곳으로 갈라지면 반드시 어긋난다)
- 유도 가능한 값은 상수로 저장하지 않고 계산으로 유도한다 (예: `MaxConsecutiveSuppressions => (int)(TotalSeconds / SuppressionCost)`)
- 기획서 원문을 XML 주석에 인용하고, 기획서가 갱신되면 주석도 함께 고친다
