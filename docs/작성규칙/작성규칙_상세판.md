# 마르코! 팀 작성규칙

> **지위**: **팀 운영 정본** — 브랜치 · 커밋 · PR · Unity 작업 · 코드 · 문서 · AI 도구 사용 규칙. 게임 규칙 · 수치의 정본은 `docs/마르코_상세기획서.md`(수치는 부록 A)이고, 이 문서는 그것을 반복하지 않는다.
> **적용 범위**: 새 레포의 모든 작업(코드 · 에셋 · 문서). 새 레포가 아직 없어 프로토타입 레포에서 작성했다 — 새 레포를 만들 때 이 파일을 `docs/작성규칙.md`로, 부록 A의 설정 파일을 레포 루트(`.github/` 포함)로 옮긴다. 프로토타입 코드는 참고용 기록이다(4.4).
> **개정 방법**: 팀원은 이슈로 제안하고, 기획이 PR로 고친다. 8절은 기획이 확정한 사항이다.
> **최종 개정**: 2026-10-09 (8절 확정 · 승인 규칙 · 레포 초기화 체크리스트 · 공용 파일 선점 · 소유자 = 기획 · 변경 요청 · GAP 닫기)
> **표기**: **필수** = 어기면 PR을 병합하지 않는다 · 권장 = 지키면 좋은 것. 규칙 끝 `[S번호]`는 맨 끝 "출처", `(사고 N)`은 9절 대응표다.

## 0. 한 장 요약 — 매일 지킬 10가지

- [ ] **1. 수치 · 규칙은 기획서에서만 읽는다.** 기획서에 없으면 코드에 넣지 말고 `[GAP]` 이슈를 연다. (1.5)
- [ ] **2. main에 직접 푸시하지 않는다.** 이슈 → 브랜치 → PR → 작성자가 아닌 프로그래머 1명 승인 → Squash 병합(기획의 `docs/` PR만 소유자 우회 — 2.3). (2.1 · 2.3)
- [ ] **3. 브랜치는 이슈 하나, 2일 안에 병합한다.** 길어지면 쪼갠다. (2.1)
- [ ] **4. 커밋 · PR 제목은 `타입(영역): 요약 (§절)`.** 기획서에 근거가 있는 변경은 §절이 필수다. (2.2)
- [ ] **5. 코드와 테스트는 같은 커밋.** 테스트가 깨진 채 푸시하지 않는다. (2.2 · 4.3)
- [ ] **6. 하루를 마치기 전에 자기 브랜치에 푸시한다.** 로컬에만 있는 작업을 남기지 않는다. (2.2)
- [ ] **7. 씬 · 공용 프리팹 · 공용 에셋은 고정 이슈 "공용 파일 선점 현황"에 댓글로 선점 공지한 뒤 연다. 해제는 PR 병합 후.** 충돌이 나면 병합하지 말고 나중에 잡은 사람이 다시 한다. 툴을 돌렸으면 씬을 저장한다. (3.4)
- [ ] **8. 에셋과 `.meta`는 같은 커밋.** 이동 · 이름 변경 · 삭제는 Unity 에디터에서 한다. (3.2)
- [ ] **9. 서버는 클라이언트가 보낸 값을 믿지 않고, 레지스트리 값은 필드에 저장하지 않는다.** (4.3)
- [ ] **10. AI가 만든 코드도 같은 PR · 리뷰 · 테스트를 거친다.** (7.2)

| 이슈 · PR 본문 | 제안 · 논의 | 누구나 |

- 권장 — 새 문서는 첫머리에 지위 한 줄을 둔다: `> **지위**: 정본 / 표현 정본 / 기록 / 제안 — 정본은 ○○`. 이유: 기록 문서를 현행 규칙으로 읽으면 옛 값으로 만든다(프로토타입 지시서 5종을 `archive/`로 옮긴 이유).

### 1.2 정본은 하나

- **필수** — 같은 값 · 규칙을 두 문서에 쓰지 않는다. 다른 곳은 `(§6.2)`처럼 참조만 한다. 이유: 정본이 둘이면 반드시 어긋난다(사고 2). [기획서 §0 문서 갱신 원칙]
- **필수** — 기획서 절 번호(§X)는 바꾸지 않는다. 절을 없애면 결번으로 둔다. 이유: 절 번호는 코드 주석 · 이슈 · 다른 문서의 참조 주소다. [기획서 §0 · 11절]

### 1.3 기획서 변경 절차 (기획)

1. 부록 A 수치를 먼저 고친다 → 2. 본문 해당 절 → 3. §0 개정 이력에 한 줄 요약 → 4. 변경 전 원문은 `docs/개정이력_YYYY-MM-DD.md`에 남긴다 → 5. 기획서 PR 병합.

- **필수** — 수치가 바뀌는 코드 PR은 그 기획서 PR이 병합된 뒤에 올린다. PR 본문에 근거 절(§X)을 적는다. 이유: 코드가 먼저 바뀌면 코드가 정본이 된다. 기획서는 기획만 고친다 — 구현자는 `[GAP]` 이슈로 요청한다(8절 2번).

### 1.4 마크다운 표기

- 날짜 `YYYY-MM-DD`, 문서 안 짧은 날짜 태그 `[MM-DD]`, 파일 참조 `` `docs/파일.md` ``, 줄 참조 `파일:줄`, 절 참조 `§6.2` 또는 `6.2절`. 제목은 `#` 문서 1개 · `##` 절 · `###` 소절까지. 수치 표에는 단위를 붙인다.
- 강조 취소선(`~~`)은 쓰지 않는다 — 바뀐 내용은 개정이력으로 옮긴다. [기획서 §0 10-03 행]

### 1.5 기획 질문(GAP) 절차

| 단계 | 누가 | 무엇을 |
|---|---|---|
| 기획서에 없거나 모순인 지점 발견 | **누구나** | 이슈 `[GAP] §절 질문` + 라벨 `gap` |
| 결정 | **기획만** | 이슈에 결정 · 근거를 적는다 |
| 반영 | 기획 | 1.3 절차로 기획서 PR(본문에 `Closes #N` — 해당 GAP 이슈) |
| 구현 | 담당자 | 기획서 PR 병합 후 코드 PR(`Closes #이슈`, 실기 확인이 필요한 작업은 `Refs #이슈` — 5.3) |

- **필수** — 결정 전에는 코드에 값을 넣지 않는다(임시값 포함). 막히면 그 작업은 `blocked` 라벨을 달고 다른 이슈를 잡는다. 이유: 코드에 만든 값이 기획서 대신 정본이 된다(사고 7). [팀_역할배분 4.1 · 6.3]
- **필수** — 기획은 `[GAP]` 이슈에 **24시간 안에 1차 답변**한다. 확정이 아니면 "검토 중 + 답변 예정 시각"을 적는다. 이유: 5~6주 일정에서 막힌 작업이 쌓이지 않게 한다. (운영 약속이다 — 기획서 수치가 아니므로 부록 A에 넣지 않는다.)
- **필수** — `blocked` 라벨은 기획서 PR이 병합된 뒤, GAP 이슈를 연 사람이 관련 작업 이슈에서 뗀다.
- **필수** — 기획서 PR 본문에 `Closes #N`(해당 GAP 이슈)을 쓴다. 병합되면 GAP 이슈가 자동으로 닫힌다. 기획서가 바뀌지 않는 답변이면 기획이 답변을 남기고 GAP 이슈를 직접 닫으며, 그때 같은 방식으로 `blocked`를 뗀다. 이유: 열린 GAP이 쌓이지 않고 막힌 작업의 해제 시점이 분명해진다. [S22]
- **필수** — 표기: 새 GAP은 이슈 번호(`#12`), 프로토타입 GAP은 "프로토 GAP-12"로 쓴다. 이유: 옛 `GAP-12`와 새 이슈 `#12`의 번호가 겹쳐 서로 다른 것을 가리키게 된다. 기존 문서(기획서 · 맵설계 · 프로토타입 기록)의 `GAP-N`은 모두 프로토타입 GAP이다.

## 2. 브랜치 · 커밋 · PR

### 2.1 브랜치

- **전략: GitHub Flow + 짧은 기능 브랜치.** `main` 하나와 이슈별 작업 브랜치만 둔다. [S15][S35] — 비교는 부록 B-1
- **필수** — `main`에 직접 커밋 · 푸시하지 않는다(보호 규칙을 걸기 전의 첫 커밋만 예외 — 2.6). 이유: 리뷰 없이 들어간 변경이 프로토타입의 호출부 누락 · 계층 위반을 만들었다(사고 4 · 5).
- 권장 — 브랜치 수명은 **2일 이내**. 넘길 것 같으면 이슈를 쪼갠다. 이유: 오래 산 브랜치일수록 씬 · enum 충돌이 커진다(사고 3 · 8).
- **필수** — 이름은 `타입/이슈번호-영문-소문자-설명`.

| | 예 |
|---|---|
| 좋은 예 | `feat/12-valve-reflow-timer` |
| 좋은 예 | `fix/31-knock-reset-on-round-start` |
| 나쁜 예 | `minsu-work` — 무엇을 하는지 · 어느 이슈인지 알 수 없다 |

### 2.2 커밋

- **필수** — 형식: `타입(영역): 한국어 요약 (§절)` — Conventional Commits를 따른다(스코프 = 영역). `(§절)`은 기획서에 근거가 있는 변경에 필수이고, `art` · `chore`는 생략할 수 있다. [S26]
  - 타입: `feat` 기능 · `fix` 버그 · `test` 테스트만 · `refactor` 동작 변화 없는 정리 · `docs` 문서 · `art` 아트 에셋 · `chore` 설정 · 패키지
  - 영역: `core` · `sound` · `net` · `ui` · `map` · `art` · `docs` · `config`(패키지 · ProjectSettings · 설정 파일) (2.3 리뷰 요청 매핑과 같다)

| | 예 |
|---|---|
| 좋은 예 | `feat(core): 밸브 역류 타이머 추가 (§6.1-2)` |
| 좋은 예 | `fix(net): 탈출 요청에서 역할을 서버가 읽도록 수정 (§14.2)` |
| 나쁜 예 | `수정` — 무엇을 · 왜 · 어느 절인지 없다 |

- **필수** — 코드 + 그 코드의 테스트는 같은 커밋. enum · 인터페이스를 바꾸면 영향받는 곳 전부를 같은 커밋에. 이유: 나중에 붙이는 테스트는 붙지 않고, 나눠 넣은 enum 변경은 다른 계층을 조용히 깨뜨린다(사고 8). [팀_역할배분 4.1 · 6.2]
- **필수** — 컴파일 오류 · 테스트 실패 상태로 푸시하지 않는다. [팀_역할배분 6.2]
- **필수** — 그날 작업은 끝나기 전에 자기 브랜치에 커밋 · 푸시한다. 이유: 디스크에만 있던 기획 표가 덮어쓰기 사고로 사라졌다(사고 1).

### 2.3 PR(풀 리퀘스트 — 병합 요청)

- **필수** — PR 제목은 2.2 커밋 형식과 같다. 이유: Squash 병합 때 PR 제목이 `main`의 커밋 메시지가 되려면 레포 설정에서 Squash 기본 메시지를 PR 제목으로 해 두어야 한다(2.4 · 2.6). 설정이 없으면 커밋이 1개인 PR은 그 커밋 메시지가 `main`에 남는다. [S18][S40]

| | 예 |
|---|---|
| 좋은 예 | `feat(sound): 신음 파문 6초 주기 발생 (§5.1-2)` |
| 좋은 예 | `fix(ui): 탈출자 관전 화면에서 목숨 슬롯 숨김 (§3.3-3)` |
| 나쁜 예 | `민수 작업분 올립니다` — 병합 후 `main` 기록에서 무엇인지 알 수 없다 |
- **필수** — 본문은 템플릿(부록 A-4)을 채운다: 근거 절 · 변경 전/후 · 테스트 · 범위 밖으로 남긴 것 · `Closes #이슈`(실기 확인이 필요한 작업은 `Refs #이슈`, 5.3). [S19][S22]
- 권장 — 변경 400줄 이하(자동 생성 `.meta` · 씬 YAML 제외). 이유: 리뷰어가 한 번에 코드를 직접 열어 볼 수 있는 크기(팀 기준).
- **필수** — 승인은 **작성자가 아닌 프로그래머 1명**이 한다(P1~P4 중 순환 지정 가능). 이유: GitHub는 PR 작성자의 본인 승인을 허용하지 않는다. [S41]
- **필수** — 영역 오너(아래 표)는 **리뷰 요청 대상**이다 — 필수 승인자가 아니다. 해당 영역을 건드리는 PR은 오너를 리뷰어로 지정하고, 변경 요청(오너 · 승인자 누구든)이 남아 있으면 해소될 때까지 병합하지 않는다. 작성자가 대응한 뒤 24시간 안에 요청자의 응답이 없으면 소유자가 해소 여부를 판단한다(운영 약속 — 기획서 수치가 아니므로 부록 A에 넣지 않는다).
- **필수** — `docs/`(기획서 · 맵설계 · 연출 등 문서) 변경은 **기획만 PR을 올린다.** 프로그래머 PR에 `docs/` 변경이 섞여 있으면 병합하지 않는다. 구현자는 `[GAP]` 이슈로 요청한다(1.5).
- **필수** — 레포 소유자는 기획이다. 기획의 `docs/` PR은 소유자 우회(bypass)로 병합한다. 우회 권한은 경로로 제한할 수 없으므로 규칙으로 제한한다: **소유자는 자기 `docs/` PR에만 우회를 쓴다.** 우회로 병합할 때도 PR을 거치고 템플릿을 채운다. `docs/` 밖의 PR(`CLAUDE.md` · `.github/` · 루트 파일 포함)은 기획이 올려도 작성자가 아닌 프로그래머 1명이 승인한다. `docs/`와 다른 파일을 한 PR에 섞지 않는다. [S39]

| 영역 | 오너(리뷰 요청 대상) | | 영역 | 오너(리뷰 요청 대상) |
|---|---|---|---|---|
| `core` | P1 | | `ui` | P4 |
| `sound` | P2 | | `art` · `map` | 디자인 (+ 배선은 P4) |
| `net` | P3 | | `docs` | 기획 |
| `config` | P3 | | | |

- 영역과 폴더(프로토타입 폴더 기준, `팀_역할배분.md` 2.4 · 2.6과 같다): `sound` = 소리 시스템 — `Core`의 `SoundPulse` · `Sound` · `Voice` · `Breath`와 `Presentation`의 `Sound` · `SoundPulse` · `Voice`(네임스페이스 `Marco.Presentation.Sound` · `Marco.Presentation.Voice`). `ui` = 그 밖의 `Presentation`. 파문을 화면에 그리는 코드(`PulseVisualRenderer` 등)는 판정(P2)과 표현(P4)이 맞물리므로 두 오너를 모두 리뷰어로 지정한다(`팀_역할배분.md` 4.1).

- **필수** — 병합은 **Squash and merge**만 쓴다. 병합 후 브랜치를 지운다. 이유: PR 하나 = `main` 커밋 하나라 되돌리기 · 주간 일지 집계가 쉽다(부록 B-2). [S15][S18]
- 권장 — 작업 중이면 Draft PR로 먼저 올린다(진행 상황 공유).

### 2.4 main 보호 (레포 설정)

- **필수** — `main`에 보호 규칙(룰셋)을 건다: PR 필수 · 승인 1(작성자 제외, 2.3) · 새 푸시 시 이전 승인 무효화 · 강제 푸시 금지 · 삭제 금지. 우회 목록에는 소유자(= 기획) 1명만 넣고, 우회 방식은 "For pull requests only"(PR을 열어야만 우회)로 한다. 이유: 규칙을 사람이 아니라 GitHub가 막게 한다. [S16][S17][S39]
- **필수** — 소유자가 `Settings > General > Pull Requests`에서 Squash 병합만 켜고 다른 병합 방식은 끄고, 병합된 브랜치는 자동 삭제하게 한다(2.1 · 2.3). Squash의 기본 메시지는 PR 제목("the pull request title")으로 정한다(드롭다운 이름은 UI에서 확인). 이유: 2.3의 "PR 제목 = `main` 커밋 메시지"가 이 설정에 의존한다. [S18][S40]
- **필수** — 레포는 **비공개**로 하고, 레포 소유자(= 기획)가 학생 팩 GitHub Pro를 받아 위 보호 규칙을 건다(8절 1번). 소유자는 팀원 전원을 협업자(쓰기 권한)로 초대한다. 이유: GitHub Free의 비공개 레포에서는 브랜치 보호 · 룰셋 · CODEOWNERS를 쓸 수 없다. [S16][S17][S21][S25]

### 2.5 충돌 · rebase · 강제 푸시

- **필수** — 강제 푸시(`--force`) 금지 — `main`과 모든 공유 브랜치. 이유: 남이 받아 간 커밋을 지우면 그 사람 작업이 꼬인다. [S9]
- **필수** — `main` 최신 내용은 자기 브랜치에 **merge**로 받는다(`git merge origin/main`). rebase는 아직 푸시하지 않은 내 커밋에만. [S9]
- 씬 · 프리팹 충돌은 3.4, 코드 충돌 절차는 5.4.

## 3. Unity 작업 규칙

### 3.1 버전 · 직렬화

- **필수** — Unity **6000.5.4f1**로만 연다(`ProjectSettings/ProjectVersion.txt`). 다른 버전으로 열지 않는다. 업그레이드는 이슈로 요청하고 기획이 결정한다. 이유: 버전이 바뀌면 전 에셋이 재직렬화돼 모든 PR이 충돌한다. (8절 4번)
- **필수** — `Edit > Project Settings > Editor > Asset Serialization > Mode = Force Text`, `Edit > Project Settings > Version Control > Mode = Visible Meta Files`. 프로토타입 레포는 둘 다 이미 이렇게 설정돼 있다. [S1][S2]
- **필수** — 같은 화면의 **Reduce version control noise**를 새 레포 첫 커밋 전에 켠다(YAML 참조를 한 줄로 써 diff가 줄어든다). 켜는 순간 많은 파일이 다시 써지므로 첫 커밋 전에만. [S2] (8절 8번)

### 3.2 `.meta` 파일

- **필수** — 에셋과 `.meta`는 같은 커밋에 넣는다. `.meta`만 빠지면 다른 사람 PC에서 GUID가 새로 생겨 참조가 끊긴다. [S1]
- **필수** — `.meta`를 손이나 스크립트 · AI로 만들거나 고치지 않는다. 이동 · 이름 변경 · 삭제는 Unity Project 창에서 한다. 이유: 수기 생성 meta가 GUID 중복 · 불완전 meta를 여러 번 만들었다(사고 10).
- 권장 — PR diff에 내가 건드리지 않은 `.meta` 변경이 있으면 원인을 확인하고 빼낸다.

### 3.3 `.gitignore` · `.gitattributes` · Git LFS

- **필수** — 부록 A-1 · A-2 파일을 레포 루트에 둔다. 생성 파일(`Library/` · `Temp/` · `Logs/` · `UserSettings/` · `Builds/` · 루트의 `*.csproj` · `*.sln` · `*.slnx`)은 커밋하지 않는다. 이유: 프로토타입 레포는 루트 csproj 14개 · slnx 2개가 추적돼, Unity가 다시 만들 때마다 그중 13개가 "수정됨"으로 남았다(사고 10). [S7]
- **필수** — 바이너리 에셋(이미지 · 오디오 · 모델 · 영상 · 폰트)은 **레포를 만들 때부터 Git LFS**로 관리한다. 팀원 PC마다 `git lfs install`을 한 번 실행한다. 이유: GitHub는 100 MiB 넘는 파일을 막고, 이미 커밋된 파일은 나중에 LFS로 옮겨도 옛 커밋에 원본이 남는다 — 레포 크기를 줄이려면 히스토리 재작성(`git lfs migrate`)이 필요하고 이는 강제 푸시 금지와 부딪힌다. [S10][S12][S14][S38]
- LFS 무료 한도는 저장 10 GiB · 대역폭 10 GiB(월). 대용량 원본(`.psd` 레이어 원본 등)은 레포 밖에 둔다. [S13]
- **필수** — 레포 밖에 둘 개인 파일: `CLAUDE.local.md`, 개인 작업 폴더(예: `Claude outputs/`). 부록 A-1에 포함돼 있다.

### 3.4 씬 · 프리팹 편집권

- **필수** — 씬(`Assets/Scenes/*.unity`) · 공용 프리팹(`Player.prefab` 등) · 아래 **공용 에셋**은 **선점 공지 → 편집 → 커밋 · 푸시 · PR 병합 → 해제 공지**. 병합 전까지 그 파일을 다른 사람이 열지 않는다. 이유: 텍스트 병합이 사실상 불가능하거나 여러 사람이 동시에 건드리기 쉬워, 동시에 고치면 한쪽 작업이 사라진다. 푸시만 하고 해제하면 다음 사람이 병합 전의 낡은 `main`에서 열어 재작업이 생긴다(사고 3). [팀_역할배분 6.1]
  - 공용 에셋(프로토타입 경로 기준): `Assets/DefaultPrefabObjects.asset` · `Assets/InputSystem_Actions.inputactions` · `Assets/Settings/*` · `Assets/_Project/Settings/SceneCondition.asset` · `ProjectSettings/*`
  - 공지 채널: 고정 이슈 1개 **"공용 파일 선점 현황"**에 댓글로 쓴다. 선점: "`Game.unity` 잡습니다", 해제(PR 병합 후): "놨습니다".
- **필수** — 씬 · 프리팹 충돌이 나면 **병합하지 않는다.** 나중에 잡은 사람이 최신 `main`에서 자기 작업을 다시 한다. [팀_역할배분 6.1]
- **필수** — 에디터 툴을 실행하거나 컴포넌트를 붙였으면 씬을 저장(`Ctrl+S`)한 뒤 커밋한다. 커밋 전에 씬 탭에 `*`(저장 안 됨) 표시가 없는지 본다. 이유: 툴을 돌리고 저장하지 않아 `PulseNetworkSync`가 씬에 붙지 않은 채 실기를 했다(사고 3). [수동검증_절차 §16-0]
- 권장 — 씬에는 프리팹 인스턴스만 두고 내용은 프리팹에서 고친다. 변형은 Prefab Variant로. 이유: 프리팹 파일은 씬보다 작게 나뉘어 선점 범위가 좁아진다. [S5]
- 권장 — 지금의 애디티브 씬 구조(`Boot` · `MainMenu` · `Lobby` · `Game`)를 유지한다. 씬 담당자는 8절 5번 표를 따른다. [S4]
- 권장 — 각자 UnityYAMLMerge를 `git mergetool`로 등록해 둔다(부록 A-7). 단 씬 충돌 해결 수단으로 기대하지 않는다 — 자동 병합 규칙 밖의 경우는 충돌로 남는다. [S3]

### 3.5 폴더 · 이름

- **필수** — 우리 코드는 `Assets/_Project/` 아래 계층 폴더(`Core` · `Net` · `Presentation` · `Editor` · `Tests`)에만 둔다. 네임스페이스는 `Marco.<계층>.<시스템>`(asmdef `rootNamespace`와 같다).
- **필수** — `Assets/FishNet/`은 외부 코드다. 고치지 않는다(필요하면 P3 이슈). 이유: 업데이트 때 덮어써져 수정이 사라진다.
- 권장 — 에셋 파일 이름은 PascalCase · 공백 없음. 기존 결정은 유지한다: 1인칭 팔 클립 `FP_` 접두어(연출.md 12.2 · 15.8). 아트 폴더는 8절 5번 구조(`Assets/_Project/Art/…`)를 쓴다.

### 3.6 어셈블리(asmdef) 의존 방향

- **필수** — 참조 방향은 지금 구조 그대로다: `Core` → 없음 / `Net` → `Core` + `FishNet.Runtime` / `Presentation` → `Core`(+ Input System · UI) / `Editor` · `Tests`는 에디터 전용. `Net`과 `Presentation`은 서로 참조하지 않고 `Core`의 인터페이스로 연결한다. asmdef 참조를 추가하려면 그 계층 오너를 리뷰어로 지정한다. 이유: asmdef가 컴파일로 막아 주는 것은 `Core`가 `Net` · `Presentation` · FishNet을 참조하는 것과 `Net` ↔ `Presentation` 상호 참조다. [S6] [팀_역할배분 9]
- **필수** — `Core`의 `UnityEngine.Time` · `Input` · `Physics` · `MonoBehaviour` 사용 금지(4.2-h)는 컴파일로 강제되지 않는다. `Core.asmdef`의 `noEngineReferences`가 꺼져 있고(`Core`가 `Vector3` 같은 값 타입을 쓴다) 이 설정은 바꾸지 않는다. 리뷰(5.1-5)와 PR 체크리스트로 확인한다.

### 3.7 패키지

- **필수** — `Packages/manifest.json` · `packages-lock.json` 변경은 **단독 PR**, 이유와 영향을 적고 P3를 리뷰어로 지정한다. 이유: 받는 순간 전원의 Library가 다시 만들어진다.

### 3.8 FishNet 재직렬화 · 프리팹 등록

- **필수** — 씬에 NetworkObject를 추가 · 이동 · 삭제했으면 그 사람이 `Tools > Fish-Networking > Utility > Reserialize NetworkObjects`를 실행하고 **씬을 저장**해 같은 커밋에 넣는다. 씬 오브젝트 SceneId가 0이 아닌지 확인한다. [S31] [수동검증_절차 §12 · §14-1]
- 권장 — 클라이언트에서 다른 프리팹이 스폰되면 `Refresh Default Prefabs`를 실행하고 `DefaultPrefabObjects.asset` 변경을 커밋한다(평소에는 자동). 이 파일은 선점 공지 대상이다(3.4). [S31]

### 5.2 PR 보고 형식

PR 템플릿(부록 A-4)과 같다 — ① 근거 절 ② 변경 전/후(값 · 조건식 · 시그니처) ③ 계산 검증(수치 PR만, 경계값 포함 실제 수치) ④ 테스트(신규 · 갱신 이름, 통과 수) ⑤ 범위 밖으로 남긴 것.

- **필수** — 문제가 하나라도 남으면 "완료"로 보고하지 않는다. [밸브 구현 지시서 1.2]
- **필수** — 이슈 · 지시와 기획서 · 기존 기록이 충돌하면 구현하지 말고 먼저 이슈에 알린다. [밸브 구현 지시서 1.3 · 팀_역할배분 7.2]

### 5.3 완료 기준(Definition of Done)

이슈를 닫는 조건 — 전부 충족:

1. 근거 기획서 절이 PR에 있고, 코드 수치가 부록 A와 같다.
2. EditMode 테스트를 추가 · 갱신했고 전부 통과한다(문서 · 아트 PR은 해당 없음).
3. 작성자가 아닌 프로그래머 1명이 승인했고(영역 오너는 리뷰 요청 대상) `main`에 병합됐다. 기획의 `docs/` PR은 소유자 우회로 병합한다(2.3).
4. 실기가 필요한 기능은 주간 실기에서 확인했다 — 그 작업의 PR은 `Closes`가 아니라 `Refs #이슈`를 쓰므로 병합해도 이슈가 자동으로 닫히지 않는다. `실기-미확인` 라벨을 달아 두고, 실기를 통과한 뒤 이슈를 직접 닫는다.

### 5.4 충돌 해결 절차

1. 자기 브랜치에서 `git fetch` → `git merge origin/main`.
2. 코드 충돌: 해결 → 컴파일 · EditMode 테스트 → 커밋 · 푸시. 상대 코드의 뜻을 모르면 그 파일 오너와 화면 공유로 푼다.
3. 씬 · 프리팹 충돌: 3.4 — 병합하지 않고 나중에 잡은 쪽이 다시 한다.
4. 강제 푸시로 해결하지 않는다(2.5).

## 6. 이슈 · 일정 · 기록

### 6.1 이슈 · 라벨 · 보드

- **필수** — 모든 작업은 이슈에서 시작한다(브랜치 이름이 이슈 번호를 쓴다). 제목: `[유형] 요약 (§절)`.

| | 예 |
|---|---|
| 좋은 예 | `[기능] 배수구 작업 시간 T 계산 (§6.5-2)` |
| 좋은 예 | `[GAP] §6.2-1 출구 파문이 탈출자에게도 들리나` |
| 나쁜 예 | `밸브 이상함` — 무엇이 · 어디서 · 기대와 어떻게 다른지 없다 |

- 라벨: 유형 `기능` · `버그` · `gap` · `아트` · `문서` / 영역 `core` · `sound` · `net` · `ui` · `art` · `map` · `docs` · `config` / 상태 `blocked` · `실기-미확인`. 레포 초기화 때 만든다(2.6).
- 보드: GitHub Projects 칸반 4열 — `할 일` · `진행 중` · `리뷰` · `완료`. [S23]
- 템플릿: 부록 A-5(기능 · 버그 · GAP). [S20]
- GAP 이슈는 기획서 PR의 `Closes #N`으로 닫힌다(1.5).

### 6.2 실기 검증 · 태그

- **필수** — 주 1회 고정 실기(최소 3인 — 호스트 1 + exe 2). 결과는 이슈로 남긴다. [팀_역할배분 4.2 · 7.4]
- 권장 — 실기 빌드를 만든 `main` 커밋에 태그 `play-YYYY-MM-DD`. 완성 빌드는 `v1.0`. 이유: 실기에서 본 버전으로 돌아갈 수 있다.

### 6.3 목요일 개발일지

- 집계 범위: 지난 목요일 ~ 이번 수요일에 `main`에 병합된 PR. Squash 병합이라 `main` 커밋 = PR이다.
- 뽑는 방법(권장): ① `git log origin/main --since=YYYY-MM-DD --pretty="%ad %s" --date=short` ② 또는 GitHub Release 화면의 "Generate release notes"(병합 PR · 기여자 자동 목록, 라벨로 분류 — 부록 A-6). [S24]
- 형식: 이번 주 병합 PR(영역별) · 실기 결과 · 다음 주 계획 · 막힌 것(`gap` · `blocked` 이슈).

### 6.4 CHANGELOG · ADR

- CHANGELOG 파일은 두지 않는다 — Release 노트(6.3)가 대신한다.
- ADR(설계 결정 기록)은 따로 두지 않는다 — 게임 결정은 기획서 §0 개정 이력 + `개정이력_YYYY-MM-DD.md`, 기술 결정은 이슈에 남긴다. 이유: 같은 결정을 두 곳에 쓰면 정본이 둘이 된다(1.2). [S37]

## 7. AI 도구(Claude Code) 사용

### 7.1 `CLAUDE.md`

- **필수** — 레포 루트에 `CLAUDE.md`(부록 A-8)를 둔다. Claude Code는 매 세션 시작 때 이 파일을 읽는다. 200줄 이하로 유지한다. [S32]
- 권장 — `CLAUDE.md` 변경은 PR로 하고 기획에게 리뷰를 요청한다. 개인 설정은 `CLAUDE.local.md`(커밋 안 함). [S32]
- 알아 둘 것 — `CLAUDE.md`는 참고 맥락이지 강제 설정이 아니다. 규칙 강제는 리뷰(5.1)가 한다. [S32]

### 7.2 AI 산출물

- **필수** — AI가 쓴 코드 · 문서도 같은 이슈 · 브랜치 · PR · 리뷰 · 테스트를 거친다. 리뷰어는 AI 산출물이라고 덜 보지 않는다.
- **필수** — AI가 제안한 수치는 기획서 부록 A와 대조하기 전까지 쓰지 않는다. 기획서에 없으면 1.5 GAP.
- **필수** — 한 AI 세션은 한 이슈 · 한 브랜치 범위에서만 일한다. 이유: 여러 명의 AI가 같은 파일을 동시에 고치는 충돌을 막는다.
- **필수** — 씬 · 프리팹 · `.meta` YAML을 AI로 직접 편집하지 않는다. Unity 에디터나 에디터 툴로 바꾼다. 이유: 자동 생성기가 불완전 meta · GUID 중복을 만들었다(사고 10).

### 7.3 AI 사용 표기

- **브랜치 커밋과 PR에 필수** — AI가 작성에 참여한 브랜치 커밋에 `Co-Authored-By:` 트레일러를 남기고, PR 템플릿의 "AI 사용" 칸에도 적는다(프로토타입 레포의 방식, 8절 7번).
- `main`의 Squash 커밋에는 트레일러가 남지 않을 수 있다 — Squash 기본 메시지가 PR 제목이기 때문이다(2.4). 추적은 PR 번호(제목 끝 `(#N)`)로 한다. GitHub가 트레일러를 Squash 커밋으로 옮기는 방식은 **확인 필요(첫 PR 병합 후 결과로 확정)**. 자동으로 넣는 Claude Code 설정 이름도 확인 필요.

## 부록 B. 조사 요약 — 영역별 비교와 선택

### B-1. 브랜치 전략

| 방식 | 장점 | 단점 | 우리 조건에서 |
|---|---|---|---|
| **GitHub Flow**(main + 기능 브랜치 + PR) [S15] | 규칙이 적다, GitHub 기능과 맞물린다 | 릴리스 분리 없음 | **채택** — 5~6주 · 배포 1회 |
| 짧은 기능 브랜치 / 트렁크 기반 [S35] | 충돌이 작다, 통합이 잦다 | 기능 플래그 · CI가 사실상 필요 | **일부 채택** — 브랜치 수명 2일만 가져옴 |
| Git Flow(develop · release · hotfix) [S36] | 릴리스 버전 관리에 강하다 | 브랜치 종류가 많아 학생 팀이 안 지킨다 | 미채택 |

### B-2. 병합 방식 [S18]

| 방식 | 장점 | 단점 | 선택 |
|---|---|---|---|
| Merge commit | 기록 그대로 | `main` 기록이 지저분, 주간 집계가 어렵다 | 미채택 |
| **Squash and merge** | PR = 커밋 1개, 되돌리기 · 집계 쉬움 | 중간 커밋 기록이 `main`에서 사라진다(PR에는 남음) | **채택** |
| Rebase and merge | 선형 기록 | 커밋 SHA가 새로 생기고, 중간 커밋이 그대로 쌓인다 | 미채택 |

### B-3. 커밋 메시지

| 방식 | 선택 |
|---|---|
| **Conventional Commits** [S26] — `타입(스코프): 설명` | **채택**(설명은 한국어, 절 번호 덧붙임). 이 레포의 기존 커밋도 `docs: …` 형식이다 |
| 자유 형식 | 미채택 — 주간 집계 · 검색이 안 된다 |
| 이모지(gitmoji) | 미채택 — 규칙 추가 대비 이득 없음 |

### B-4. 씬 충돌 방지

| 방식 | 장점 | 단점 | 선택 |
|---|---|---|---|
| **선점 공지**(고정 이슈 댓글) | 도구 없음, 이미 팀 규칙 | 사람이 잊으면 끝 | **채택**(팀_역할배분 6.1) |
| Git LFS 파일 잠금(`lockable`) [S11] | 도구가 막는다 | 씬은 LFS 대상이 아니어서 텍스트 파일 잠금 설정이 따로 필요, GitHub 지원 범위 **확인 필요** | 미채택(출시 후 재검토) |
| UnityYAMLMerge [S3] | 일부 충돌 자동 해결 | 규칙 밖은 충돌로 남는다, 각자 설정 필요 | 보조(권장) |
| 씬 분할 · 프리팹화 [S4][S5] | 충돌 범위 축소 | 구조 변경 비용 | 권장(기존 애디티브 구조 유지) |

### B-5. Git LFS

| 선택 | 이유 |
|---|---|
| **레포 생성 때부터 사용** | 아트 1명이 5~6주간 모델 · 텍스처 · 오디오를 넣는다. GitHub는 100 MiB 초과 파일을 막고[S14], 나중에 옮기면 옛 커밋에 원본이 남아 줄이려면 히스토리 재작성(`git lfs migrate`)이 필요하다[S38]. 무료 10 GiB 저장 · 대역폭[S13] — 프로토타입 `Assets/`가 16 MB라 여유 |

### B-6. CI(GameCI · GitHub Actions)

| 선택 | 이유 |
|---|---|
| **보류**(3주차 재판단, 출시 후 도입 후보) | GameCI는 Unity 라이선스 파일 · 계정 이메일 · 비밀번호를 레포 시크릿으로 등록해야 한다[S33]. 학생 개인 라이선스 · 2단계 인증 계정으로 설정하는 데 드는 시간과, 6000.5.4f1 이미지 제공 여부(**확인 필요**)를 5~6주 일정에서 감당하기 어렵다. 대신 PR 본문에 로컬 EditMode 결과를 적는다(4.3). 도입하면 테스트만 자동화하는 Test Runner 액션부터 쓴다[S34] |

### B-7. 일부러 뺀 관행

| 관행 | 뺀 이유 |
|---|---|
| Git Flow · release 브랜치 | 배포 1회, 브랜치 종류가 많으면 안 지킨다 |
| 승인 2명 이상 | 4명 중 2명이 묶이면 병목. 1명으로 확정(8절 6번) |
| CODEOWNERS 강제 | GitHub Pro 비공개 레포라 쓸 수는 있지만[S21], 리뷰어 지정은 2.3 영역 표로 충분해 강제하지 않는다 |
| 서명 커밋 · 선형 기록 강제 | 학생 팀 설정 비용 대비 이득 없음 |
| CI · 자동 빌드 | B-6 |
| LFS 파일 잠금 | B-4 |
| CHANGELOG 파일 · ADR | 6.4 — 정본이 둘이 된다 |
| `.editorconfig` 빌드 오류 강제 | 경고 폭주 — 표시만(A-3) |
| 기능 플래그 | 트렁크 기반의 전제지만 우리 규모에 과하다 |
